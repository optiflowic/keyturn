# GitHub

What keyturn uses on GitHub: the workflow that runs the gate and the merge conditions' check on a task's pull request, the workflow that detects what reached the default branch without them, the script that pushes the task branch and opens its pull request, the script that posts the reviews on it, and the script that merges it, with the one-time setup of a repository ([ADR 0041](../docs/adr/0041-agents-push-task-branches-and-open-pull-requests.md), [ADR 0042](../docs/adr/0042-pm-merges-on-machine-checked-conditions.md), [ADR 0046](../docs/adr/0046-acceptance-record-conditions-check-and-merge-script.md), [ADR 0048](../docs/adr/0048-default-branch-guarded-in-three-layers.md)).

## The workflow

[`workflows/keyturn-gate.yml`](workflows/keyturn-gate.yml) runs two checks on every pull request that is not a draft. Both fail a pull request whose branch is not a task's (`task/<task>`) or that does not go to the default branch.

- `keyturn gate` runs `gates/gate.sh --task <task> --default-branch origin/<default branch>`: the gate finds the base and the other roles' commits from the branch and its state file itself ([ADR 0043](../docs/adr/0043-gate-finds-a-task-s-range-in-ci.md)).
- `keyturn conditions` runs `gates/conditions.sh` with the same arguments: no high or medium finding open in the two review reports (a medium finding of `review` accepted on an answered decision card excepted), both reports reviewing up to the developer's last commit, and the client's acceptance recorded for the acceptance guide and the delivery report at the head, with nothing but the approvals and the state file changed after them ([ADR 0046](../docs/adr/0046-acceptance-record-conditions-check-and-merge-script.md)). It reads committed records only, so it needs no stack tools. It fails until the client accepts, as it should.

On a draft pull request, both jobs take other names, `keyturn gate (draft, not checked)` and `keyturn conditions (draft, not checked)`, and fail in their first step, in seconds; marking it ready, and every push after, runs both checks under their own names ([ADR 0051](../docs/adr/0051-draft-checks-fail-under-other-names.md)). A task's pull request is a draft until the `deliver` step commits the delivery documents and marks it ready; `deliver` runs the gate locally on every round before that, and the merge conditions need the checks only on the head that is merged, so a task stays within GitHub Free's included compute (about 2 billed minutes per push of a draft). Neither job is ever skipped: GitHub counts a skipped required check as passed, and a draft's check under a required check's name could stand in for the head's ([ADR 0043](../docs/adr/0043-gate-finds-a-task-s-range-in-ci.md)). `merge.py` and the detecting workflow pass over a draft's runs, and do not count a skipped check as a pass.

A person adds it to the project once:

1. Copy it to `.github/workflows/keyturn-gate.yml` in the project.
2. Set `KEYTURN_COMMIT` to the full SHA of the keyturn commit to check with (the one the project's tasks run with).
3. Keep the tool steps of the profiles that `parts` in `keyturn/config.json` names, and remove the others. For a `go` part, set `go-version-file` to that part's `go.mod`.
4. Commit it on the default branch. On a plan with branch protection, also require both checks, as "One-time setup" below says.

On a pull request, GitHub runs the workflow as the pull request's branch has it, so a branch that changed it would run its own version. What keeps it as the person committed it is the agents' token: without the Workflows permission, GitHub refuses a push that changes a file under `.github/workflows/` ([ADR 0042](../docs/adr/0042-pm-merges-on-machine-checked-conditions.md)). The gate also fails such a change as one to a protected path (the CI jobs that run the gates, "Guardrails" 1), but that check runs inside the workflow, so it is not what protects it. A token with that permission, or a person's own push, can change it; the one-time setup gives the agents only the token without it.

The workflow's steps install the tools the profiles need (`profiles/<name>/README.md`, "Tools"): Go and `golangci-lint` v2 for `go`, Node.js 22 or later for `react-spa`. The gate records their versions; it does not pin them ([ADR 0037](../docs/adr/0037-gate-records-tool-versions.md)).

## The detecting workflow

[`workflows/keyturn-watch.yml`](workflows/keyturn-watch.yml) runs the check `keyturn watch`, from [`scripts/watch.py`](scripts/watch.py) at the keyturn commit it names, on every push to the default branch and to `task/**`, on the deletion of a branch, every six hours, and when a person starts it by hand ([ADR 0048](../docs/adr/0048-default-branch-guarded-in-three-layers.md), layer 2). Without branch protection, nothing on GitHub refuses a push that goes around keyturn's scripts; this workflow finds it afterwards and tells the maintainer. With branch protection, it still finds a reset or a deleted task branch, so it is added on every plan. Each run checks:

- **Every commit on the default branch** after the starting commit the workflow names (`KEYTURN_START`), on its first-parent history up to the tip, not only the pushed ones, so a push that skipped workflows (`[skip ci]` and the like) is found by the next run. A commit passes only when it is the merge commit of a merged pull request from a `task/<task>` branch of this repository to the default branch, with one parent, the tree of that pull request's head, and a head that contains its parent and changes no file under `.github/workflows/`; the newest run of `.github/workflows/keyturn-gate.yml` for that head, from its pull request, passed with its jobs `keyturn gate` and `keyturn conditions` (read as `merge.py` reads it, a draft's runs passed over, [ADR 0049](../docs/adr/0049-workflow-runs-read-instead-of-check-runs.md)); and `gates/conditions.sh` passes on that head again. Two kinds pass without a pull request: a commit that changes only files under `.github/workflows/` (the agents' token cannot push one), and a commit whose full SHA the maintainer lists in the repository variable `KEYTURN_VOUCHED`. The starting commit, and the default branch's tip that the newest earlier passing run checked, must still be ancestors of the tip, or the branch was reset.
- **The repository's activity** (GitHub's "List repository activities"), which records every push, force push, branch creation and deletion, and pull request merge (`pr_merge`), whether or not a workflow ran for it. It is read after a checkpoint: the later of the repository variable `KEYTURN_CHECKED_UNTIL` and the start of the newest earlier passing run, less an hour. The hour is there because the activity can list a push after a run has started: a passing run that started before an entry appeared would otherwise move the checkpoint past it, and no later run would read it. An entry read twice is checked twice, with the same result. A run with no earlier passing run and no `KEYTURN_CHECKED_UNTIL` fails, since it has nothing to read the activity after; the one-time setup sets the variable before the first run. A run fails on a force push or a deletion of the default branch, a push to it whose commit is no longer on it, a force push to a `task/**` branch (a task branch's history is trusted, [ADR 0043](../docs/adr/0043-gate-finds-a-task-s-range-in-ci.md)), and the deletion of one (it is the task's record, [ADR 0047](../docs/adr/0047-after-the-client-does-not-accept-a-delivery.md)). A run started by a push or a deletion first waits up to five minutes for the activity to list it, and fails when it does not.

When a run fails, it opens an issue with the workflow's `GITHUB_TOKEN` that lists each commit, push, or deletion and why, and mentions the maintainer named in the repository variable `KEYTURN_MAINTAINER`; while that issue is open, a later run that finds something else comments on it, and one that finds the same says nothing more. Nothing else in the issue mentions anyone: an `@` from a commit, a branch, or a report is broken. The failed check also stops `merge.py`, which merges only after `keyturn watch` passed on the default branch's tip since its last push, so no task merges on top of a commit nobody vouched for.

The variables are the maintainer's: the agents' token has no Variables, Issues, or Workflows permission, and only reads Actions, so the agents cannot vouch for a commit, move the checkpoint, turn the workflow off, delete its runs, close the issue, or change the workflow. That holds only while agents run with that token alone ("One-time setup", step 5). `watch.py` exits 0 when everything passed, 1 when something did not, and 2 when it could not run (an issue is opened then too, when it can be). Its tests: `python3 -m unittest discover -s github/scripts`.

### Recovering after a failed run

A failure stays in the activity after it is put right, so every later run fails until the checkpoint moves past it, and no task merges meanwhile. The maintainer, not an agent, from GitHub's settings or a terminal of their own ([ADR 0048](../docs/adr/0048-default-branch-guarded-in-three-layers.md), "Recovering after a failed run"):

1. Look at what the issue lists: the commits, pushes, force pushes, or deletions, and who made them (the run's log has the same).
2. Put it right: revert the commit or reset the default branch, restore a deleted or force-pushed task branch from a local copy (`git push origin <the commit>:refs/heads/task/<task>`, with `--force` for a force-pushed one), or, for a commit of your own, add its full SHA to `KEYTURN_VOUCHED` (Settings → Secrets and variables → Actions → Variables). A reverted commit stays in the default branch's history, which every run checks in full, so add the full SHAs of both the commit and its revert to `KEYTURN_VOUCHED` once you have looked at them; `KEYTURN_CHECKED_UNTIL` moves only where the activity is read from, never which commits are checked. A reset removes the commit from the history instead, and is a force push the activity records, which step 3 moves past. Until a task branch is restored, the commits merged from it are reported as "not in the clone": the workflow reads a merged head from the branches.
3. Set `KEYTURN_CHECKED_UNTIL` to the time of the last activity you looked at, your own pushes of step 2 included, in ISO 8601 (for example `2026-11-22T10:00:00Z`), so that the runs read only what came after it. The commits on the default branch are still checked in full; the checkpoint moves only where the activity is read from.
4. Start `keyturn watch` by hand (Actions → keyturn watch → Run workflow), check that it passes, and close the issue. Then resume a task that waits for its merge.

## Pushing and the pull request

[`scripts/task_branch.py`](scripts/task_branch.py) is how `deliver` reaches GitHub ([ADR 0041](../docs/adr/0041-agents-push-task-branches-and-open-pull-requests.md)):

- `push <task>` pushes `HEAD` to `refs/heads/task/<task>` on `origin`, only when the current branch is `task/<task>` and is not the default branch, without force and without running Git's hooks, so a push that would rewrite the remote branch is refused.
- `open <task>` opens the task's pull request as a draft, to the default branch, or updates the description of the one that is open. The description carries the delivery report's "Summary" and "What you need to do" once the report is committed, and links the client's documents on the branch at the pushed commit; it never copies the acceptance guide. It never acts on a pull request from a fork.
- `ready <task>` writes the description again from the head, and marks the pull request ready for review.
- `close <task>` closes the task's pull request with a comment, never merging it, when the state file at the pushed head says `Status: closed`: the client chose to stop the task ([ADR 0047](../docs/adr/0047-after-the-client-does-not-accept-a-delivery.md)). The branch is kept as the record; a closed task does not hold up the next one.
- A task has one pull request. When it was closed or merged, `open` and `ready` stop, and never open another one or reopen it: the maintainer decides what happens ([ADR 0044](../docs/adr/0044-task-branch-and-pull-request-kept-in-step-with-origin.md)). The state file does not record the pull request; the branch finds it.

It needs the GitHub CLI (`gh`), with `GH_TOKEN` set to the agents' token ("One-time setup", step 4). The recommended permission rules deny the plain `git push` and the `gh pr` commands that change a pull request (`adapters/claude/README.md`). They stop the plain commands; permission rules match a command's text, so they cannot close every way around the script. What reaches the default branch is guarded in three layers: the scripts, the detecting workflow, and branch protection where the plan has it ([ADR 0048](../docs/adr/0048-default-branch-guarded-in-three-layers.md)). Its tests: `python3 -m unittest discover -s github/scripts`.

### When the task branch on origin moved

`task/<task>` on `origin` may have commits the local branch does not (pushed from another machine, or by a person). The push is then refused, since it is never forced, and the task stops, waiting for the maintainer; `resume` reports the branches as diverged ([ADR 0044](../docs/adr/0044-task-branch-and-pull-request-kept-in-step-with-origin.md)). Agents push only through the push script, and the client never touches the code, so in keyturn's flow this does not happen; when it does, the commits are discarded. The commits are never taken into the task branch.

The maintainer looks at those commits (`git fetch origin`, then `git log task/<task>..origin/task/<task>`) and discards them: if you added the ruleset that blocks force pushes on `task/*` ("With branch protection", step 2), turn it off for this one push, overwrite the remote branch with the local one from a terminal of your own (`git push --force-with-lease=task/<task>:origin/task/<task> origin task/<task>`), and turn the ruleset on again right after. The detecting workflow fails on that force push, since a task branch's history is trusted, and you put it right as its recovery steps say ([ADR 0048](../docs/adr/0048-default-branch-guarded-in-three-layers.md), "Recovering after a failed run"). Then resume the task.

To keep a change those commits made, discard them all the same, and ask for the change again as a change to the requirements (`spec`), so that it goes through every role and check.

## Posting the reviews

[`scripts/post_findings.py`](scripts/post_findings.py) posts the findings of a committed `review` or `security-review` report on the task's pull request ([ADR 0045](../docs/adr/0045-deliver-posts-the-review-reports-on-the-pull-request.md)). `deliver` runs it after every push, and `resume` after its own, as `post_findings.py <task> <review | security-review> <the report's commit>`, with the newest commit the state file lists for that role:

- It reads the report at that commit, never from the working tree, and needs the pull request to be at the local head (it waits a few seconds for GitHub to see the push).
- It posts one review with the event `COMMENT`: a pull request's author cannot approve it or request changes on it, and the agents and the client may share one account. A finding whose location is a line, or a range of lines, of the pull request's diff at the reviewed head (the head in the report's "Reviewed change") is a line comment on that commit; every other open finding is in the review's text, with the report's summary and a link to the committed report. Fixed findings are listed by number. If GitHub refuses the review as unprocessable (HTTP 422, for example one line it cannot place in its diff, which refuses them all), every finding goes in the text; any other failure is not retried, since the review may have been created.
- Each review's text ends with a hidden marker, `<!-- keyturn-findings: <role> <report blob> <report commit> -->`. The script reads the markers of that role in the reviews by the signed-in account: when the newest one names the same report, it posts nothing; otherwise it compares with the report at that marker's commit, and posts only new findings, findings whose status, location, or text changed (a finding whose line moved is posted again at its new line), and the numbers of findings no longer in the report; when none changed, it posts nothing.
- An `@name` in a report notifies nobody: the report quotes code and documents, which are data.
- The post is not a merge condition; the committed report is ([ADR 0042](../docs/adr/0042-pm-merges-on-machine-checked-conditions.md)). A failed post does not stop the task, and the next push tries again.

It exits 0 when it posted or had nothing new to post, 1 when it was refused (no open pull request, it was not pushed, or GitHub refused the post), and 2 when it could not run (a wrong branch, no origin, no `gh`, no report at the commit). The recommended permission rules deny `gh api`, `gh issue comment`, `gh alias set`, and `gh auth` too. The deny rules stop the plain commands. Permission rules match a command's text, so they cannot close every way around the scripts. The merge conditions are decided by the committed reports and CI, though ([ADR 0042](../docs/adr/0042-pm-merges-on-machine-checked-conditions.md)), so a post made around the script does not change the merge decision. Its tests: `python3 -m unittest discover -s github/scripts`.

## Merging

[`scripts/merge.py`](scripts/merge.py) is the only way `deliver` and `resume` merge a task's pull request, in the `merge` step, after the client's acceptance is recorded ([ADR 0046](../docs/adr/0046-acceptance-record-conditions-check-and-merge-script.md)). It checks itself what branch protection would, so that it holds on a plan without it ([ADR 0048](../docs/adr/0048-default-branch-guarded-in-three-layers.md)). `merge.py <task>`, on `task/<task>`:

- refuses a pull request that is not open, still a draft, goes to another branch than the default one, or comes from a fork (a fork's pull request runs the fork's workflow, [ADR 0043](../docs/adr/0043-gate-finds-a-task-s-range-in-ci.md)), and one whose head is not the local `HEAD` and `task/<task>` on `origin`;
- refuses a head that does not contain the default branch's tip on `origin` ("up to date"). A task branch is never updated from the default branch ([ADR 0031](../docs/adr/0031-documents-fixed-once-implement-starts.md)), so when the default branch moved after the task started, the task stops for the maintainer;
- refuses a head that changes a file under `.github/workflows/` against that tip, so that the gate's run on its pull request is the default branch's workflow, not one the branch brought ([ADR 0049](../docs/adr/0049-workflow-runs-read-instead-of-check-runs.md));
- waits up to 9 minutes (`--wait-minutes`) for the gate's workflow to finish on that head, since the push right before starts it ([ADR 0044](../docs/adr/0044-task-branch-and-pull-request-kept-in-step-with-origin.md)), and refuses unless it passed. It reads the newest run of `.github/workflows/keyturn-gate.yml` for that head, from a `pull_request` event in this repository, through GitHub Actions' API, and needs the run and its jobs `keyturn gate` and `keyturn conditions` to have concluded `success`; a run whose jobs were skipped does not pass. It passes over a draft's runs, whose jobs have other names ([ADR 0051](../docs/adr/0051-draft-checks-fail-under-other-names.md)), so a draft's run newer than the ready one neither counts nor hides it. A fine-grained token has no Checks permission, so the runs are read, not the check runs ([ADR 0049](../docs/adr/0049-workflow-runs-read-instead-of-check-runs.md));
- waits, in the same time, for the detecting workflow, `.github/workflows/keyturn-watch.yml` and its job `keyturn watch`, on the default branch's tip, read the same way, counting only a run that started after the last push to the default branch in the repository's activity, so that an old success on a commit the branch was reset to does not count; it refuses when that run failed, or when the activity lists no push to the default branch. When `.github/workflows/keyturn-watch.yml` is not on the default branch, it refuses, with branch protection too: protection prevents a push, but does not find a reset or a deleted task branch;
- waits, in the same time, for the newest run of `keyturn watch` on the head itself, which the push of the task branch starts, and refuses when it failed: that run finds a force push to the task branch, which the tip's run, started before it, does not ([ADR 0050](../docs/adr/0050-merge-script-reads-watch-on-the-task-head.md));
- runs `gates/conditions.sh` of its own keyturn copy on that head;
- squash-merges naming that head (`sha`), so that GitHub refuses the merge if the head moved meanwhile. A merge GitHub refused is never tried again;
- checks the merge commit: its only parent must be the tip it checked, and its tree the head's. The default branch can still move between the check and the merge; when it did, the pull request is merged, and the task stops for the maintainer, who looks at the merge commit (`keyturn watch` fails on it too).

It exits 0 when it merged, 1 when it refused (the message says why), 2 when it could not run, 3 when the checks have not finished, or GitHub does not show the pushed head on the pull request or the tip in the activity yet (`deliver` then runs it again, up to about an hour), and 4 when it merged but the merge commit is not the checked head on the checked tip. `merge.py <task> --protection` prints `protected` when the default branch's protection (a ruleset or a classic rule) requires both checks, `not protected` when GitHub showed both the rules and the branch and neither does, and `not known` when either could not be read, and merges nothing; `deliver` uses it for the delivery report, which says, for `not known`, that it could not be checked. On a private repository on GitHub Free, GitHub answers the rules with 403 ("Upgrade to GitHub Pro or make this repository public"), and a token that lacks a permission gets a 403 too, so a 403 is never read as `not protected`. The recommended permission rules deny `gh pr merge` and `gh api`. Its tests: `python3 -m unittest discover -s github/scripts`.

## One-time setup

A person sets up each project repository once, before its first task. Do it in GitHub's settings of the repository, as an administrator, and not with the agents' token. Every plan needs "On every plan"; a repository whose plan has branch protection and rulesets (a public repository, or a paid plan) also gets "With branch protection" ([ADR 0048](../docs/adr/0048-default-branch-guarded-in-three-layers.md)).

### On every plan

This works on a private repository on GitHub Free. Without branch protection, a push to the default branch that goes around keyturn's scripts is detected, not prevented, and each delivery report says so.

1. **The gate's workflow.** Add it as "The workflow" above says, and commit it on the default branch yourself.
2. **The detecting workflow.** First, before you commit any workflow, add the repository variables under Settings → Secrets and variables → Actions → Variables: `KEYTURN_MAINTAINER` (your GitHub account, which the issue mentions; a run without it fails, so that what it finds always reaches someone) and `KEYTURN_CHECKED_UNTIL` (the time now, in ISO 8601 and UTC, for example `2026-11-22T10:00:00Z`); add `KEYTURN_VOUCHED` when you first vouch for a commit. The push that adds the workflow runs it at once, and a run with no earlier passing run and no `KEYTURN_CHECKED_UNTIL` fails, since it has nothing to read the activity after (it opens an issue, and the next run after you set the variable passes; close that issue then). Then copy [`workflows/keyturn-watch.yml`](workflows/keyturn-watch.yml) to `.github/workflows/keyturn-watch.yml` in the project. Set `KEYTURN_COMMIT` to the same keyturn commit as the gate's workflow, and `KEYTURN_START` to the full SHA of the default branch's tip before you add keyturn's workflows (every commit after it is checked), and change `main` under `push` if the default branch has another name. Commit both workflows on the default branch yourself, in a commit that changes nothing else, and push it from a terminal of your own (the agents' token cannot push a workflow; with an HTTPS `origin`, push it with the SSH URL, as step 5 says). Check that the run the push started passed, or start `keyturn watch` once by hand (Actions → keyturn watch → Run workflow) and check that it passes, so that the default branch's tip has a passing check before the first task. Until it is there, `merge.py` refuses, on every plan. A workflow of the project that deploys on a push to the default branch should wait for `keyturn watch` to pass (`workflow_run`).
3. **Outside contributors.** Under Settings → Actions → General, in "Approval for running fork pull request workflows from contributors", choose "Require approval for all external contributors", so that no workflow runs on someone else's pull request before you look at it.
4. **The agents' token.** Create a fine-grained personal access token for this repository only ("Only select repositories"), with the repository permissions Contents: Read and write, Pull requests: Read and write, Actions: Read-only (`merge.py` reads the runs of keyturn's workflows and their jobs), and Metadata: Read, and nothing else: no Administration, no Workflows, no Variables, no Secrets, no Issues, no Commit statuses, and no write access to Actions. A fine-grained token has no Checks permission ([ADR 0049](../docs/adr/0049-workflow-runs-read-instead-of-check-runs.md)). Without Workflows, GitHub refuses the agents' pushes that change a workflow; without Variables, Issues, and write access to Actions, they cannot vouch for their own commits, move the checkpoint, close the detecting workflow's issue, or turn the workflow off, start it, re-run it, or delete its runs; without Administration, they cannot change the rulesets; without Commit statuses, they cannot post a status that stands in for a check. The repository's activity, which `merge.py` reads too, needs Metadata: Read only. On a private repository on GitHub Free, this token was refused each of those changes with 403 (#149).
5. **Run the agents with that token alone.** Start the session that runs the agents with `GH_TOKEN` set to the agents' token (for example, `GH_TOKEN=<the agents' token> claude`), never with your own `gh` login, and let Git push with it: give the project's clone an HTTPS `origin` (`https://github.com/<owner>/<repository>.git`), and run `gh auth setup-git` with `GH_TOKEN` set, which makes Git ask `gh`, which answers with `GH_TOKEN`. An SSH `origin` (`git@github.com:...`) pushes with your own SSH key instead, which can change the workflows. Once `origin` is HTTPS, your own pushes go through `gh` too, and GitHub refuses one that changes a workflow, since `gh`'s token has no `workflow` scope ("refusing to allow an OAuth App to create or update workflow ... without `workflow` scope"). When you change a workflow (adding them in steps 1 and 2, or a new `KEYTURN_COMMIT`), push from a terminal of your own with the SSH URL, for example `git push git@github.com:<owner>/<repository>.git main`. Do not add the `workflow` scope to your `gh` token: your login is on the same machine as the agents (#119), and with that scope it could change the workflows too. The recommended permission rules deny `gh auth`, `gh variable`, `gh secret`, `gh workflow`, `gh run`, and `security` (macOS's credential store, where your own credentials are too; the session needs only the token you pass it). If the session runs with your login, or any token with more permissions, an agent can vouch for its own commits, turn the detecting workflow off, or change the rulesets, and only the scripts and the permission rules are left.
6. **Check it.** Open a pull request from a branch that is not a task's, and mark it ready: both checks must fail. While it is a draft, `keyturn gate (draft, not checked)` and `keyturn conditions (draft, not checked)` fail instead, and no check named `keyturn gate` or `keyturn conditions` appears on it.

### With branch protection

On a public repository, or a paid plan, also add these. They prevent what the detecting workflow only detects; the steps above stay.

1. **The default branch.** Under Settings → Rules → Rulesets, add a branch ruleset that targets the default branch, with "Enforcement status" Active, an empty bypass list (so it applies to administrators too), and these rules:
   - "Restrict deletions" and "Block force pushes";
   - "Require a pull request before merging", with "Allowed merge methods" including Squash;
   - "Require status checks to pass", with "Require branches to be up to date before merging", and the checks `keyturn gate` and `keyturn conditions`, each with GitHub Actions as its source.
2. **The task branches.** Add a second branch ruleset that targets `task/*`, Active, with an empty bypass list, and "Restrict deletions" and "Block force pushes" ([ADR 0043](../docs/adr/0043-gate-finds-a-task-s-range-in-ci.md)).
3. **Check it.** The pull request of "On every plan", step 6, must have its merge button blocked.

### A pull request of your own

A pull request from a branch that is not a task's (for example, one that updates the workflow or the keyturn commit it names) fails both checks, and stays so: an exception for the maintainer alone is phase 7. To merge it, look at it; with branch protection, turn the default branch's ruleset to Disabled for that one merge, merge it, and turn it to Active again right after, turning off nothing else, and never leaving it off while a task runs. The detecting workflow fails on that merge commit, unless it changes only files under `.github/workflows/`, until you vouch for it ([ADR 0048](../docs/adr/0048-default-branch-guarded-in-three-layers.md)): add the merge commit's full SHA to `KEYTURN_VOUCHED`, and start `keyturn watch` by hand again; it passes when nothing else is wrong, since a commit on the default branch is checked again on every run. A commit you push to the default branch yourself is the same (you can add its SHA before you push it). A run that failed meanwhile opened an issue: close it once a run passes. When you change `KEYTURN_COMMIT`, change it in both workflows, in one commit that changes only them.
