# 0069. QA checks the look on the screens with Playwright, at the design's checked widths, and commits the screenshots as the client's evidence

- Status: accepted
- Date: 2026-11-26

## Context

The requirements have a required "Look" section, whose criteria (the tidy minimum at least) are ordinary acceptance criteria ([ADR 0066](0066-requirements-ask-about-the-look-once.md)), and the design says how they are met: the "Checked widths" and one row per look criterion in "How the look's criteria are met", naming the tokens and the rule that meet it ([ADR 0067](0067-design-decides-how-the-look-is-built.md)). Nobody checks them on the screens yet. QA's web tests in the `react-spa` profile run in `jsdom`, which does not lay pages out, so no test can see where a label sits or whether a page scrolls sideways; the reviewer reads the diff and does not see the screens either. In the worked example, AC-10 to AC-13 are `not tested`, and the acceptance guide asks the client to check them by hand.

What constrains the answer:

- QA tests from the requirements and never reads the implementation; it already reads the design for how to reach the deliverable ("QA's tests", "Stack", "Libraries and external services", the interfaces in "Structure").
- A new tool is checked before it is adopted, development tools a profile approves included ("Guardrails" 3, [ADR 0054](0054-newest-stable-versions-checked-against-the-runtime.md)), and every role installs packages without running their install scripts ([ADR 0055](0055-installs-skip-install-scripts.md), [ADR 0056](0056-gate-fails-new-packages-with-install-scripts.md)). A browser test tool also downloads a browser, which is not an npm package and does not come through the registry.
- The gate reads committed files, runs in temporary worktrees and in CI, and needs no network beyond the setup's `npm ci`.
- The client is to judge the look from evidence: here, screenshots in the acceptance guide; later, a client-facing test report that carries QA's evidence for every criterion (#200), which uses the same screenshots. Comparing against an approved look (pixel diff, #197) and a designer's check (#198) come later.

## Options considered

1. **Playwright Test as a `react-spa` profile tool, run by QA only.** QA's look tests open the running deliverable in Chromium at the design's widths, measure what can be measured, and take screenshots; the gate type-checks, lints, and formats the tests, but does not run them, so neither the gate nor CI downloads a browser. A later change that breaks the look is found by QA's rerun in the next round, not by the gate.
2. **The same, and the gate runs the tests too.** A change that breaks the look fails the gate; but every gate run, CI included, downloads a browser from outside the registry, and the gate needs the deliverable running (for `react-spa`, a server for the API it calls), which its checks do not start today.
3. **Vitest's browser mode with its Playwright provider.** The look tests run in `vitest run`, so the gate runs them; the same browser download in every gate run and in CI, and more packages in the profile, for tests that render components alone, without the pages as the deliverable serves them.
4. **Keep the client's checks by hand.** Nothing new to trust, but the client does the builder's work, and nothing records what was checked or how.

## Decision

Option 1.

**The tool.** The `react-spa` profile approves `@playwright/test` as a profile tool for QA's check of the look; it brings `playwright` and `playwright-core`, its only dependencies. The design lists it with its kind and check when the deliverable has screens, `conventions` installs it at the design's version as the profile's other tools, and the gate's `pinned-tools` check keeps the three packages where `conventions` put them. The profile names no version ([ADR 0054](0054-newest-stable-versions-checked-against-the-runtime.md)); each project's design checks the one it takes. The check done for adopting it into the profile, on 2026-11-26:

- Version: 1.65.1, the newest stable release, published on 2026-11-13, past the 7-day waiting period (1.66.0 exists only as an alpha).
- Name: the packages Playwright's documentation names, from the repository `microsoft/playwright`; no look-alike.
- Publishers: the same maintainers on the registry as the releases before, publishing through GitHub Actions in `microsoft/playwright` as a trusted publisher. 1.65.1 is the first release published by a new patch-release workflow of that repository (`publish_manual.yml`, started by a maintainer), from the commit on `release-1.65` just before the tag `v1.65.1`, which only sets the version; the earlier releases came from the tag through `publish_release.yml`. That is a change in how it is published, not in who publishes it: weighed, and accepted.
- Provenance: an npm provenance attestation (SLSA v1) for each of the three packages, naming that repository, workflow, and commit.
- Install scripts: none in any of the three; their lock entries have no `hasInstallScript`.
- Known vulnerabilities: none for 1.65.1 in OSV. The one advisory, GHSA-7mvr-c777-76hp (browsers downloaded without verifying the TLS certificate), affects releases before 1.55.1.
- Maintenance and license: maintained (the repository was pushed the same day), Apache-2.0.
- Runtime: `engines` asks for Node.js 20 or later; tried with Node.js 26.13.1, the newest LTS release.

**The browser and where it comes from.** QA uses Chromium's headless shell only, installed with `node node_modules/@playwright/test/cli.js install chromium --only-shell` in the part's folder, into Playwright's cache outside the repository, never with `npx` or `npm exec` (ADR 0055), and never with `--with-deps`, which runs the system's package manager with administrator rights. What it downloads, and from where, is fixed by the `playwright-core` the lock file installs (its `browsers.json` and its code), so the package's integrity hash and provenance also fix the browser it fetches:

- Chrome Headless Shell (159.0.8154.6 for 1.65.1) from `https://cdn.playwright.dev/builds/cft/<version>/<platform>/`, which redirects to Google's Chrome for Testing bucket (`https://storage.googleapis.com/chrome-for-testing-public/`), the same file Google's own list of Chrome for Testing downloads names (compared on 2026-11-26 for `mac-arm64`: the same SHA-256).
- FFmpeg, which Playwright installs with any Chromium and uses only to record videos, which QA does not record, from Playwright's own builds at `https://cdn.playwright.dev/dbazure/download/playwright/builds/ffmpeg/`, with fallbacks at `playwright.download.prss.microsoft.com` and `cdn.playwright.dev`.

Playwright downloads them over HTTPS with the certificate checked, but checks no hash or signature of the archives (the macOS binary carries only an ad-hoc signature). So QA checks the source before every install: it runs the same command with `--dry-run` first, and installs only when every "Download url" and fallback it prints starts with `https://cdn.playwright.dev/` or `https://playwright.download.prss.microsoft.com/`, and when no `PLAYWRIGHT_DOWNLOAD_HOST` or `PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST` variable is set, which would send the download elsewhere. QA never sets them; when one is set, or a URL is another, it stops and asks whoever runs it. The test report records the browser and its version.

**With `--ignore-scripts`.** None of the three packages runs an install script, so `npm ci --ignore-scripts` installs them as they are, and no `- Allows install scripts:` line is needed. Playwright never downloads a browser on install: only its `install` command does, which is not an npm lifecycle script, so ADR 0055 neither allows nor forbids it, and the gate's `install-scripts` check has nothing to find. This decision is what allows that download: for QA only, for Chromium's headless shell (with the FFmpeg it brings), from the sources above. The gate and CI never download a browser, and no other role runs Playwright in the MVP.

**Where the tests are and what the gate does with them.** QA's look tests are Playwright test files in `qa/look/` of the part, named `*.spec.ts`, with their config in `qa/playwright.config.ts`, which writes Playwright's own output outside the repository. Vitest's `include` names only `*.test.ts` and `*.test.tsx`, so `vitest run` does not take them; the gate type-checks, lints, and formats them as any file of the part, and runs none of them. QA runs them against the deliverable started as "How to run" says, at the address it gives.

**What QA checks.** QA reads the design's "Look": "Checked widths", and "How the look's criteria are met", with the rows of "Tokens" those name, for their values. Each row is how the design makes its criterion measurable, and the client agreed to the design, so a measured value that differs from the row fails the criterion, as a measured value that misses the criterion itself does. For every look criterion in scope, QA's tests open each page the criteria cover, at the phone width, at the desktop width, and on both sides of each breakpoint (at it, and one pixel below it), and measure what can be measured: for the tidy minimum, that there is space between a label and its field, that buttons with the same role have the same height and line up and overlap nothing, that the page does not scroll sideways and nothing ends past its right edge, and that every control reached with Tab shows a focus outline; and the values the design's row names. They take a full-page screenshot of each page at the phone width and the desktop width, and one at the desktop width with the first control focused with Tab. QA then looks at every screenshot, judges against each criterion what cannot be measured (for example, that it is clear which label belongs to which field, or that no text is cut off), and writes the result per criterion in the test report, with what was measured, what was judged, and the screenshots.

**Where the screenshots go.** QA commits them in `keyturn/client/evidence/<task>/`, as PNG files named `<page>-<width>.png` and `<page>-<width>-focus.png`, with the task's name (with `deliver`, the task's; on its own, one the person gives). They are evidence for the client, not QA's working files: the acceptance guide shows them now, and the client-facing test report of #200 shows the same files. A rerun replaces the task's screenshots, and removes those it no longer takes. A `qa` commit may change that folder, as well as QA's folders and the test report: the gate allows it (`--others qa:<commit>`), and the developer cannot change it, since `keyturn/client/**` is protected.

**What the client gets.** The acceptance guide has a section "The screens", before the steps to start the deliverable, which shows the screenshots by page, at each width, with the look criteria QA checked on them, and a line where the client writes whether they look as expected; one that does not is reported as a failed check is. A look criterion QA checked and passed is not a check the client does by hand any more; one QA could not check, or checked only in part, stays a check by hand, as any criterion the test report marks `not tested` or `partly tested`.

## Reasons

- QA already checks behavior against the requirements in a context of its own, and a screen can be judged against the look's criteria without reading the code. A real browser is the only place where the layout exists; measuring it at fixed widths turns "tidy" into checks that pass or fail, and the screenshots let the client, and QA itself, judge the rest.
- The design's widths and rows are what ADR 0067 wrote them for: QA checks at the widths the developer built for, with the numbers the design gives, instead of choosing its own.
- Keeping the browser out of the gate keeps the gate and CI to committed files and the registry, and keeps a download of executable code from outside the registry to one role, on one machine, behind a check of where it comes from. The cost is that the gate does not catch a later change that breaks the look; with `deliver`, QA reruns every test in every round, so the round that breaks it fails in `qa`.
- Chromium's headless shell is the smallest browser Playwright offers, and it comes from Google's own Chrome for Testing bucket; Firefox and WebKit would come from Playwright's own builds, two more sources to trust.
- Screenshots in `keyturn/client/` are where the client's documents already are, so the acceptance guide, its translation, and the later client-facing test report link to them with a short relative path, and the same images serve both.

## Consequences

- `profiles/react-spa/profile.json` adds `@playwright/test`, `playwright`, and `playwright-core` to `pinned-tools`. Its `README.md` lists Playwright among the profile tools, says how QA installs the browser and checks where it comes from, where the look tests live and how the gate treats them, and lists under "What this profile does not check" that the gate runs no browser, and that QA's look checks run only in Chromium.
- `gates/gate.py` lets a `qa` commit change `keyturn/client/evidence/**`.
- `skills/qa/SKILL.md` reads "Look", installs the browser as above, writes the look tests, takes and commits the screenshots, and reports each look criterion; `templates/internal/test-report.md` has a "Look" section with a row per look criterion.
- `skills/design/SKILL.md` lists `@playwright/test` with the profile's other tools when the deliverable has screens, and writes each row of "How the look's criteria are met" so that it can be measured at the checked widths.
- `templates/client/acceptance-guide.md` and `skills/deliver/SKILL.md` show the screenshots in "The screens", and keep a look criterion in a check by hand only when QA did not check it in full; `deliver` gives QA the task's name, and accepts QA's commits to the evidence folder.
- The worked example's AC-10 to AC-13 are checked by QA, its test report has the "Look" section, its acceptance guide shows the screenshots instead of asking the client to check the look by hand, and its screenshots are taken from a small static copy of its pages built with its design's tokens, since the example has no code.
- A local translation of the acceptance guide, under `.keyturn/i18n/<lang>/`, keeps the images' relative links, which do not resolve there; the client sees the screenshots in the guide in the repository and in the pull request, and the translation's captions say what each one shows.
- Not checked: the look in Firefox and Safari; how the pages look with the fonts of another machine (the screenshots show the fonts of QA's machine); a change between two screenshots (pixel diff waits for an approved look, #197); and that a later round did not break the look between QA's runs, since the gate does not run the look tests. The browser's archive has no hash or signature that QA checks; only its source is checked.
