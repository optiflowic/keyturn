# 0069. QA checks the screens end to end in a real browser, with the E2E tool the stack profile names, and commits the screenshots as the client's evidence

- Status: accepted; "What the client gets" superseded by [0070](0070-client-test-report-and-acceptance-without-required-checks.md) (the screenshots are shown in the client's test report, and the client writes no result for them)
- Date: 2026-11-26
- Supersedes: in [0029](0029-role-commits-passed-as-arguments.md), what a `qa` commit may change: it may also change the images in the task's own folder in `keyturn/client/evidence/`; in [0033](0033-delivery-documents-from-the-records.md), the records the delivery documents are written from: also the names of the screenshots the test report lists; in [0060](0060-design-answers-for-qa-and-threat-ratings.md), what QA's questions for the design may ask: also the checked widths, when the design has none; in [0068](0068-design-answers-may-add-a-token.md), that an answer never changes the checked widths: an answer may add them when the design has none

## Context

The requirements have a required "Look" section, whose criteria (the tidy minimum at least) are ordinary acceptance criteria ([ADR 0066](0066-requirements-ask-about-the-look-once.md)), and the design says how they are met: the "Checked widths" and one row per look criterion in "How the look's criteria are met", naming the tokens and the rule that meet it ([ADR 0067](0067-design-decides-how-the-look-is-built.md)). Nobody checks them on the screens yet. QA's web tests in the `react-spa` profile run in a simulated browser that does not lay pages out, so no test can see where a label sits or whether a page scrolls sideways; the reviewer reads the diff and does not see the screens either. In the worked example, AC-10 to AC-13 are `not tested`, and the acceptance guide asks the client to check them by hand.

What constrains the answer:

- QA tests from the requirements and never reads the implementation; it already reads the design for how to reach the deliverable ("QA's tests", "Stack", "Libraries and external services", the interfaces in "Structure").
- keyturn fixes the way of working, not the tools: a stack profile names the tools for its stack, as the best practice at the time it was written, and a project's design may choose another with the client, as it chooses its styling method (ADR 0067). E2E test tools change quickly; a rule that names one would go out of date with it.
- A new tool is checked before it is adopted, development tools a profile approves included ("Guardrails" 3, [ADR 0054](0054-newest-stable-versions-checked-against-the-runtime.md)), and every role installs packages without running their install scripts ([ADR 0055](0055-installs-skip-install-scripts.md), [ADR 0056](0056-gate-fails-new-packages-with-install-scripts.md)). An E2E tool usually also downloads a browser, executable code that does not come through the package registry.
- The gate reads committed files, runs in temporary worktrees and in CI, and needs no network beyond its setup's package install.
- The client is to judge from evidence: here, screenshots in the acceptance guide; later, a client-facing test report that carries QA's evidence for every criterion, the screen operations included (#200), which uses the same screenshots. Comparing against an approved look (pixel diff, #197) and a designer's check (#198) come later.

## Options considered

1. **QA checks the screens end to end in a real browser, with the E2E tool the profile names, and only QA runs those tests.** The gate type-checks, lints, and formats them, but does not run them, so neither the gate nor CI downloads a browser. A later change that breaks the screens is found by QA's rerun in the next round, not by the gate.
2. **The same, and the gate runs the E2E tests too.** A change that breaks the screens fails the gate; but every gate run, CI included, downloads a browser from outside the registry, and the gate needs the deliverable running (for a web client, the server whose API it calls), which its checks do not start today.
3. **Component tests in a browser, run by the unit test runner.** The gate runs them, but with the same browser download in every gate run and in CI, and they render components alone, not the pages as the deliverable serves them.
4. **Keep the client's checks by hand.** Nothing new to trust, but the client does the builder's work, and nothing records what was checked or how.

## Decision

Option 1. The rule is the way of working: QA operates the deliverable's screens in a real browser, from outside, as a person does, checks them against the acceptance criteria, and keeps evidence the client can see. This decision applies it to the look's criteria; #200 applies it to every criterion checked by operating the screens. The tool that does it is not part of the rule.

**The tool.** A stack profile with screens names the E2E tool QA uses (the browser test tool, its runner, and the browser it drives) as a profile tool, chosen as the best practice for its stack at the time the profile is written, with its supply-chain check and date in the profile's `README.md`. The profile also says, for that tool: where the browser comes from and how QA checks the source before it downloads anything; how the tool works with installs that skip install scripts; where QA's E2E tests and their config live in the part; and what the gate does with them. A profile changes its tool through a change to the profile, with a new check. A project's design takes the profile's tool, as a profile tool listed with its kind and check. A design may choose another E2E tool, or choose one for a stack whose profile names none: that is an other tool, which needs the client's agreement under "Must agree", with the realistic options and a recommendation; when the client leaves it to keyturn, the architect takes the best practice at that time for the stack, checked in its current documentation (never from memory), and records it in an ADR of the project, with the date and the alternatives. QA uses only the E2E tool the design lists.

**The browser.** Only QA downloads a browser, on its own machine, outside the repository, and only from the sources the profile (or, for a tool the design chose, its ADR) names, after checking that the download goes to them; it uses one browser engine unless the design names more. A download it cannot confirm is not made. The gate and CI never download a browser, and no other role runs the E2E tests in the MVP. The browser download is never an install script: the tool's packages are installed without their scripts, as every package is (ADR 0055), and a tool whose packages need their install script to work needs the `- Allows install scripts:` line of ADR 0055 like any other; the download is the tool's own command, which QA runs by hand. A browser that cannot be installed, that QA does not download because the source cannot be confirmed, or that does not start (for example, a system library missing, which QA never installs) is a missing test environment: the criteria it was for are `not tested`, never `fail`, so the work does not go back to a developer who cannot fix it.

**Where the tests are and what the gate does with them.** QA's E2E tests live in QA's folders, where the profile says, apart from the tests the unit test runner runs. The gate type-checks, lints, and formats them as any file of the part, and runs none of them. QA runs them against the deliverable started as "How to run" says, at the address it gives.

**What QA checks.** QA reads the design's "Look": "Checked widths", and "How the look's criteria are met", with the rows of "Tokens" those name, for their values. Each row is how the design makes its criterion measurable, and the client agreed to the design, so a measured value that differs from the row fails the criterion, as a measured value that misses the criterion itself does. For every look criterion in scope, QA's tests open each page the criteria cover, at the phone width, at the desktop width, and on both sides of each breakpoint (at it, and one pixel below it), and measure what can be measured: for the tidy minimum, that there is space between a label and its field, that buttons with the same role have the same height and line up and overlap nothing, that the page does not scroll sideways and nothing ends past its right edge, and that every control reached with the Tab key shows a focus outline; and the values the design's row names. They take a full-page screenshot of each page at the phone width and the desktop width, and one at each of those widths after one press of Tab. QA then looks at every screenshot, judges against each criterion what cannot be measured (for example, that it is clear which label belongs to which field, or that no text is cut off), and writes the result per criterion in the test report, with what was measured, what was judged, what each screenshot shows, and the screenshots.

**Checked widths missing.** A design whose "Look" has no "Checked widths" leaves QA without the widths to check at. QA asks for them with a `Question for the design:` line, and the architect may answer with the widths in `keyturn/internal/design-answers.md`, as ADR 0068 lets an answer add a token: the answer only adds a phone width and a desktop width the design does not have, never changes or removes widths or breakpoints the design or an earlier answer gives, and adds no breakpoint. Until an answer gives them, the look's criteria are `not tested`.

**Where the screenshots go.** QA commits them in `keyturn/client/evidence/<task>/`, as PNG images directly in that folder, with the task's name (with `deliver`, the task's; on its own, one the person gives, which must be a task name: lowercase letters and digits with single hyphens). They are evidence for the client, not QA's working files: the acceptance guide shows them now, and the client-facing test report of #200 shows the same files. A run of every test replaces the task's screenshots, and removes those it no longer takes. A `qa` commit may change only the images in its task's folder, besides QA's folders and the test report: the gate allows them when it knows the task (`--task`, or `--evidence-task` with `--base`), and nothing else under `keyturn/client/evidence/`. The developer cannot change the folder, since `keyturn/client/**` is protected.

**What the client gets.** The acceptance guide has a section "The screens", before the steps to start the deliverable, which shows the screenshots by page, at each width, with the look criteria QA checked on them, and a line where the client writes whether they look as expected; one that does not is reported as a failed check is. A look criterion QA checked and passed is not a check the client does by hand any more; one QA could not check, or checked only in part, stays a check by hand, as any criterion the test report marks `not tested` or `partly tested`. A local translation of the guide, made with `localize`, points its images at the images in the repository, so the client sees them in the language they read.

## Reasons

- QA already checks behavior against the requirements in a context of its own, and a screen can be judged against its criteria without reading the code. A real browser is the only place where the layout exists and where a person's operations can be repeated as they are; measuring the pages at fixed widths turns "tidy" into checks that pass or fail, and the screenshots let the client, and QA itself, judge the rest.
- Fixing the way of working and leaving the tool to the profile and the design keeps the rule true when the tools change: a profile moves to a better tool with a new check, and a project can choose another with its client, without a new rule.
- The design's widths and rows are what ADR 0067 wrote them for: QA checks at the widths the developer built for, with the numbers the design gives, instead of choosing its own. Letting an answer add missing widths, and nothing else, keeps a task from stopping over a gap the design should not have had, without changing what the developer built against.
- Keeping the browser out of the gate keeps the gate and CI to committed files and the registry, and keeps a download of executable code from outside the registry to one role, on one machine, behind a check of where it comes from. The cost is that the gate does not catch a later change that breaks the screens; with `deliver`, QA reruns every test in every round, so the round that breaks it fails in `qa`.
- Screenshots in `keyturn/client/` are where the client's documents already are, so the acceptance guide and the later client-facing test report link to them with a short relative path, and the same images serve both. Limiting a `qa` commit to its own task's images keeps it from changing an earlier delivery's evidence, which the client may already have accepted.

## Consequences

- Each stack profile with screens names its E2E tool and says what this decision asks of it; `react-spa` is the first (its `README.md`, "QA's check of the screens", and its tools in `profile.json`'s `pinned-tools`). A profile without one leaves the choice to the design, with the client.
- `gates/gate.py` lets a `qa` commit change the images directly in `keyturn/client/evidence/<task>/` when it is given the task, with `--evidence-task` added for `--base`; `skills/qa/SKILL.md` and `skills/deliver/SKILL.md` pass it.
- `skills/qa/SKILL.md` reads "Look", installs the browser as the profile says, writes the E2E tests, takes and commits the screenshots, and reports each look criterion; `templates/internal/test-report.md` has a "Look" section with a row per look criterion.
- `skills/design/SKILL.md` lists the profile's E2E tool with the profile's other tools when the deliverable has screens, or chooses another with the client, writes each row of "How the look's criteria are met" so that it can be measured at the checked widths, and may answer missing checked widths; `templates/internal/design-answers.md` has an `Adds checked widths:` line.
- `templates/client/acceptance-guide.md` and `skills/deliver/SKILL.md` show the screenshots in "The screens", and keep a look criterion in a check by hand only when QA did not check it in full; `deliver` gives QA the task's name, and accepts QA's commits to its evidence folder. `skills/localize/` rewrites the image links of a translation to the repository's images.
- The worked example's AC-10 to AC-13 are checked by QA, its test report has the "Look" section, its acceptance guide shows the screenshots instead of asking the client to check the look by hand, and its screenshots are taken from a small static copy of its pages built with its design's tokens, since the example has no code.
- Not checked: the look in the browser engines QA did not use; how the pages look with the fonts of another machine (the screenshots show the fonts of QA's machine); a change between two screenshots (pixel diff waits for an approved look, #197); and that a later round did not break the screens between QA's runs, since the gate does not run the E2E tests. What the profile's tool cannot check about the browser it downloads (for example, a hash or a signature) is listed in the profile's "What this profile does not check".
