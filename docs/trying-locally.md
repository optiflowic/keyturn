# Trying changes locally

How to try a change to keyturn on your own machine before opening a pull request. Read only the items for what you changed; this file was moved out of [`AGENTS.md`](../AGENTS.md) so that sessions that do not try anything do not load it ([ADR 0071](adr/0071-size-limits-for-agents-md-and-skills.md)). Paths and commands are from the repository root unless an item says otherwise. In a scratch repository, run keyturn's scripts by their path in your working copy (`<keyturn>/gates/gate.sh`, with `<keyturn>` the path of your working copy, unless an item gives `<keyturn>` another meaning).

- Load the plugin from your working copy for one session: `claude --plugin-dir .` (Claude Code). This uses your edits without installing anything.
- Try a template change on the worked example in `evals/requests/task-manager/example/`: fill in the changed part there as the role would, and check that it still reads well for someone who does not read code.
- Try `localize` on this repository: ask for a document, issue, or pull request in another language (for example, "Translate docs/design/concept.md into Japanese"). The translation is written under `.keyturn/i18n/<lang>/`, and `git status` must stay clean. To try the other direction, write a few lines in another language and ask for them in English as an answer to a decision card: the original, the English, and the back-translation go under `.keyturn/i18n/inbound/<lang>/`, and `git status` must still stay clean.

- Try `spec` in a scratch Git repository under `.keyturn/` (it is git-ignored), so that its commits never touch this repository: create its `keyturn/config.json` with `project-config`, then ask for requirements from `evals/requests/task-manager/request.md` and compare them with `evals/requests/task-manager/example/keyturn/client/requirements.md`. The request does not mention the look: the requirements must have a "Look" section that proposes the recommended answer, with a Must requirement and a criterion for each item of the tidy minimum, and `spec` must commit one decision card about the look with them and send it in the same message. Answer the card with "leave it to you" and approve: the approval must be recorded with no new version. Then, in another scratch repository, answer another option and approve: the version must be recorded as not approved, and the next version must write that option in "Look" without a new card. A request for a command-line tool must get `Look baseline: none (no screens)` and no card. To try a request in another language, set English-only mode and write the request in that language.
- Try `design` in such a scratch repository: commit the `.gitattributes` line `keyturn/client/*.md text eol=lf` and the example's `keyturn/config.json`, `keyturn/client/requirements.md`, and `keyturn/client/approvals.md`, ask for a design, and check that its threat model covers every case in the requirements' "Misuse" section.
- Try `implement` in a scratch Git repository under `.keyturn/`: commit the `.gitattributes` line `keyturn/client/*.md text eol=lf`, copy `keyturn/` from `evals/requests/task-manager/example/` without `internal/handoff.md`, `internal/test-report.md`, `internal/review.md`, `internal/security-review.md`, and `internal/state/`, commit it, and ask for delivery 1 (R-1 to R-4, R-7, R-8, R-10). Check that every changed path except `keyturn/internal/handoff.md` is inside the design's "Areas the work may change" and that no protected path changed, and compare the handoff notes with that example's `keyturn/internal/handoff.md`. Every `npm install` and `npm ci` the session ran must pass `--ignore-scripts`, and "How to run" must say so too.
- Try `qa` in a scratch Git repository under `.keyturn/`: commit the `.gitattributes` line `keyturn/client/*.md text eol=lf`, the example's `keyturn/config.json`, `keyturn/client/requirements.md`, `keyturn/client/approvals.md`, and `keyturn/internal/design.md`, a small deliverable (for example, the build from the `implement` trial), and handoff notes with "How to run". Ask for tests of delivery 1, check that every test is in QA's folders and that `keyturn/internal/test-report.md` has a row per acceptance criterion, and compare it with `evals/requests/task-manager/example/keyturn/internal/test-report.md`. To try it without a specification, commit the removal of `requirements.md`, answer QA's question by asking for tests of the current behavior, and check that the report says `Specification: none` and keeps the warning note. QA runs the gate on its own commits before it reports (with Go, golangci-lint v2, and Node.js installed, as in the profiles' trials): its report to you must say that the gate passed, or name only `FAIL test` lines for criteria it marks `fail`, and every commit it made must change only QA's folders, the report, and the images in `keyturn/client/evidence/<task>/`. To try a fix, commit a `.golangci.yml` with `gocyclo` at `min-complexity: 3` (as `conventions` would) before asking for the tests: QA must split its tests until the gate's `lint` passes, in a commit of its own, with no `//nolint` comment. To try a test that relies on what the gate does not have, build the web part in the working tree (its `dist/` is git-ignored) and ask, as a rerun, for an API test of the page `/signin` the server serves: it must not read `web/dist`, and it must pass in the gate. To try the look, give the trial a deliverable with screens whose design has a "Look" (for example, the `implement` trial's build with the example's design), the E2E tool its stack profile names installed by `conventions` (for `react-spa`, as its `README.md` says), and a task name: QA must check where the browser download goes before it downloads anything, as the profile says, and keep the browser outside the repository; its E2E tests must be where the profile says and open each page at the design's checked widths; it must commit the screenshots in `keyturn/client/evidence/<task>/` with its report, whose "Look" has a row per look criterion, and a screenshot of the expected result of each criterion done on the screens, which "Checks" names with its steps and what was observed, as in `evals/requests/task-manager/example/keyturn/internal/test-report.md`; and the gate on its commits, with `--evidence-task <task>`, must pass without downloading a browser. Start a session with a variable set that the profile says sends the download elsewhere (for `react-spa`, `PLAYWRIGHT_DOWNLOAD_HOST`): QA must not download the browser, and must mark the look's criteria `not tested`. Remove "Checked widths" from the design: QA must mark the look's criteria `not tested` with a `Question for the design:` line, and, with `deliver`, the architect's answer with `Adds checked widths:` must let QA check them in the next round. To try a translation, translate the client's test report with `localize`: its images must open the repository's images. To try QA fixing its tests by the maintainer's decision, stop a task from the `deliver` trial in `implement` after the gate failed on a lint finding in a QA test, once waiting for the maintainer and once at the rework limit (`Stopped because: rework limit`), and resume it with `QA fixes its tests, by the maintainer's decision: <what>`: `qa` runs before `implement`, its commits are listed as `qa`, `Rework` and its limit do not change, and once the gate passes the task goes on with `security-review`, with the `implement` row's "Commit" unchanged.
- Try `conventions` in a scratch Git repository under `.keyturn/`: copy `keyturn/config.json` and `keyturn/internal/` (without `conventions.md`) from `evals/requests/task-manager/example/`, ask for the conventions, and compare them with that example's `keyturn/internal/conventions.md`.
- Try `review` in a scratch Git repository under `.keyturn/`, created with `git init -b main`: commit the `.gitattributes` line `keyturn/client/*.md text eol=lf` and the example's `keyturn/` folder from `evals/requests/task-manager/example/` without its `internal/review.md`, then, on a new branch, commit two planted problems: `api/internal/http/signup.go` with a sign-up handler that rejects passwords shorter than 12 characters itself, while `api/internal/account/signup.go` creates the account without checking the length, and `api/internal/account/signin.go` with a variable named `cnt` for the failed sign-in counter. Ask for a review of that branch. The report must find the first as a medium `design fit` finding and the second as a low finding based on C-1 (other findings about the parts that do not exist yet may appear too); its "Reviewed change" must be the range from `main` to the branch head; it must have no "Security" section and must not rely on the handoff or the security review; and its commit must contain only `keyturn/internal/review.md`, with the Go files unchanged. Compare it with that example's `keyturn/internal/review.md`.
- Try `resume` in a scratch repository under `.keyturn/`: on a branch `task/delivery-1`, copy `evals/requests/task-manager/example/keyturn/internal/state/delivery-1.md` to `keyturn/internal/state/delivery-1.md`, change it to a stopped task, commit it, and ask to resume it. `resume` reads the committed state file, so the change must be committed first. To try the push it does first, give that repository a GitHub repository of your own as `origin` (as in the `deliver` trial), push the branch, and commit one more state change without pushing it: `resume` must push it before it goes on, also when the state file says done. To try going on before a usage reset, commit a state file stopped for a usage limit with `Can continue: after <a time tomorrow>` and ask to resume it: it must stop and say when it can continue; then say that the maintainer decided to go on now: with `usage.py check` passing (for example, made-up values below the limits, as in the usage limits' trial), the resume's History line must name the decision and `Can continue` must not have been changed before it; with the check failing, it must stop and record nothing. To try a pull request that was never opened, push the branch with `task_branch.py push <task>` alone, without `open`, and ask to resume it: with nothing left to push, `resume` must still open the draft pull request. To try a script the tool refuses, deny `task_branch.py open` with a permission rule of your own while `deliver` runs: the task must stop with `Status: stopped`, waiting for the maintainer, with the tool's message in `Can continue`.
- Try `security-review` in another scratch Git repository under `.keyturn/`, created with `git init -b main`: commit the `.gitattributes` line `keyturn/client/*.md text eol=lf` and the example's `keyturn/` folder from `evals/requests/task-manager/example/` there, without its `internal/security-review.md`, then, on a new branch, commit a small change with a planted flaw (for example, a task route that does not check who owns the task), and, in another commit, change T-1's "Mitigation" in `keyturn/internal/threat-model.md` to say it is not needed. Ask for a security review of that branch. The report must find the flaw as a high finding, find the threat model change as a high finding located at the threat model while checking T-1 as it is on `main`, count T-6 (locking another person out) as accepted only because decision card 2 meets every condition, and say which scans did not run. Other threats have no code to check and get high findings too, T-6 included: its mitigation is not implemented either, and only what it leaves is accepted. The threat model on `main` still links its "Status" lines to the left-out report; that is expected.
- Try `deliver` in a scratch Git repository under `.keyturn/`, created with `git init -b main` and one commit on `main`, with a GitHub repository of your own (private, empty) as `origin`, `main` pushed to it, and `git remote set-head origin --auto`, with an HTTPS `origin`, in a session started with `GH_TOKEN` set to an agents' token made as "One-time setup" in `github/README.md` says, never with your own `gh` login: `deliver` pushes `task/<task>` after every state commit and opens a draft pull request with the first push. Without `origin`, it must stop at the start and ask. Ask it to deliver the request in `evals/requests/task-manager/request.md`: it must create `task/delivery-1`, commit a state file that `python3 skills/resume/scripts/task_state.py check` accepts, run `spec`, and stop waiting for the client's approval, with `git status` clean and `keyturn/internal/state/delivery-1.md` saying how it can continue. Approve the requirements, record the answer with `spec`, and resume the task with `resume`: `design` runs next, and the task stops again in `design` while a decision card waits. To try the check for task branches that are not merged, keep that branch, switch back to `main`, and ask for another delivery: it must stop, list `task/delivery-1`, and start only after you answer that it should start anyway. Running a task to its last step needs the stack profiles in `profiles/` (the MVP issues that add them): before `conventions`, `deliver` writes `parts` in `keyturn/config.json` from the design's "Stack profile" line, and stops when a profile is missing; the last step commits `keyturn/client/test-report.md`, `keyturn/client/acceptance-guide.md`, `keyturn/client/delivery-report.md`, and `keyturn/internal/gate/<task>.json`, and sets the state file to done. The acceptance guide must ask no check of a criterion the test report says passed. The full request has 13 acceptance criteria, so once they are approved, `deliver` must stop before `design`, waiting for the maintainer; resume it with the maintainer's decision to go on as one delivery. With no browser for QA (for `react-spa`, with `PLAYWRIGHT_DOWNLOAD_HOST` set), the task must stop after `qa`, waiting for the maintainer, before the documents are written.
- Try posting the reviews in the scratch repository of the `deliver` trial, with a GitHub repository of your own as `origin`: on `task/<task>`, with its draft pull request open, commit `keyturn/internal/review.md` from `evals/requests/task-manager/example/` with its "Reviewed change" set to the range of a code change on the branch and one finding's location set to a changed line, push with `task_branch.py push <task>`, and run `python3 <keyturn>/github/scripts/post_findings.py <task> review <the report's commit>`. The pull request must get one comment review, with that finding as a line comment and the others in its text. Run it again: it must print `nothing new`. Set a finding to `fixed`, add one, commit, push, and run it with the new commit: only those two must be posted.
- Try the acceptance and the merge in the scratch repository of the `deliver` trial, with a GitHub repository of your own as `origin` (private on GitHub Free works) set up as "One-time setup" in `github/README.md` says ("On every plan"; "With branch protection" too where the plan has it), with `KEYTURN_COMMIT` set to a pushed commit of your working copy, and the session started with `GH_TOKEN` set to the agents' token, never with your own `gh` login, on a task that `deliver` ran to the `merge` step: it must commit an acceptance row at `waiting` and stop, waiting for the client, with `keyturn conditions` failing on the pull request. Answer with `<the client's acceptance in their language>` and record it with `spec`: the row must say `accepted` with your words next to it (in English-only mode, the English you confirmed), and `approval.py accept-status <task>` must print both. Resume the task: it must finish, wait for both checks, and merge with a squash merge, after which `task_state.py unmerged origin/main` must not list the branch. Then try the answers that are not acceptance on another task: after an answer that does not accept the delivery, the task must stop on a decision card that proposes one of the four cases of ADR 0047; answer "Ask me again" and check that a new acceptance row is added for the same documents commit; then, after another answer that does not accept it, answer "Stop the task" and check that the state file says `Status: closed`, the pull request is closed without a merge, and `task_state.py unmerged origin/main` does not list the branch. A merge from a terminal of your own (`gh pr merge --squash`) while `keyturn conditions` fails must be refused by GitHub where the repository has branch protection. Without it, `merge.py` must refuse, on another task, when a commit of your own was pushed to `main` after the task started (the head does not contain the tip), and when `keyturn watch` on `main`'s tip failed or has no run since its last push; and `merge.py <task> --protection` must print `not protected`. Translate `approvals.md` with `localize`: the fixed words must read `accepted (<translation>)`.
- Try the detecting workflow on a GitHub repository of your own (private, on GitHub Free) set up as "One-time setup" in `github/README.md` says, with `KEYTURN_COMMIT` in both workflows set to a pushed commit of your working copy, and the agents' session started with `GH_TOKEN` set to the agents' token: `keyturn watch`, started by hand, must pass. Each of these must then fail it and open one issue that mentions you, a later run commenting only when it finds something new: a commit pushed to `main` from a terminal of your own; one with `[skip ci]` in its message (no run on the push; the next scheduled run, or one started by hand, finds it); a squash merge from your own terminal of a task's pull request whose `keyturn conditions` failed; a squash merge of a task's pull request after `main` moved (GitHub's squash commit then has a tree that is not the head's); a force push to `task/<task>`; and the deletion of `task/<task>`. A task's merge through `merge.py` must pass, and so must a commit of your own once its SHA is in `KEYTURN_VOUCHED`. After a failure, the recovery steps in `github/README.md` ("Recovering after a failed run"), with `KEYTURN_CHECKED_UNTIL` set, must make it pass again. On a draft pull request, the checks must be named `keyturn gate (draft, not checked)` and `keyturn conditions (draft, not checked)` and fail, with no check named `keyturn gate` or `keyturn conditions`; marking it ready, and every push after, must run both checks under their own names.
- Try the subagents: start a session with `claude --plugin-dir .` and run `/agents`: the definitions in `adapters/claude/agents/` must be listed as `keyturn:<name>`. To check that a subagent preloads its skill, ask the session to start one (for example, `keyturn:reviewer`) as a subagent and to ask it, without tools, for the first line of its skill and the skill's base directory; it must quote the skill (for `keyturn:reviewer`, `skills/review/SKILL.md`) and give the folder in your working copy. Started as the main session (`claude --agent keyturn:reviewer`), it does not preload the skill.
- Try the permission rules in a scratch Git repository under `.keyturn/`: commit a file on `main`, add a bare repository as `origin`, and copy `adapters/claude/permission-settings.json` to `.claude/settings.local.json` there, with `<path to the keyturn plugin>` replaced by the absolute path of a checkout of your branch outside your working copy (for example, `git worktree add ../keyturn-plugin <your branch's commit>`), and start the session with `claude --plugin-dir <that path>`: with the plugin's folder above the scratch repository, the rules would deny every edit there. Any trial that runs `deliver` with these rules installed loads the plugin the same way. In a session started there, ask the agent to run, one by one, `git push origin main`, `git push`, `git reset --hard`, `git clean -fd`, `rm -rf <a folder>`, and `find . -name <a file> -delete`: each must be denied by a permission rule, also in auto mode. Ask for `gh pr create`, `gh pr ready <n>`, `gh pr review <n>`, `gh api repos/<owner>/<name>/pulls/<n>/reviews`, `gh issue comment <n>`, `gh alias set <name> api`, `gh auth token`, `gh auth status`, `gh variable set KEYTURN_VOUCHED --body <a SHA>`, `gh secret list`, `gh workflow disable keyturn-watch.yml`, `gh run list` in a repository with a GitHub remote, and `security find-generic-password -s <a name> -w`: each must be denied, while `python3 <keyturn>/github/scripts/task_branch.py push <task>` on `task/<task>` pushes only that branch, and is not denied in auto mode (with `<keyturn>` the same path as in the rules; `post_findings.py` and `merge.py` match the same way). Ask the agent to change a line of `<keyturn>/github/scripts/task_branch.py` with the Edit tool, then with `sed -i`, then by a redirection (`>`): each must be denied by a permission rule, and `git -C <keyturn> status` must show no change to that file. Then ask for `git clean -f -- <an untracked file>`, `git restore --source=HEAD --staged --worktree -- <a changed file>`, and `rm -f -- <a file>`: each must run, since the skills use them. Nothing else must reach the bare repository: `git ls-remote` lists only `refs/heads/task/<task>`, and no `main`.
- Try the usage limits: add the status line from `adapters/claude/statusline-settings.json` to your user settings, start a session with `claude --plugin-dir .`, and run `python3 adapters/claude/scripts/usage.py check` once the status line shows both windows. Replace `<path to the keyturn plugin>` in that file with the path of your working copy. To try `check` and `hook` with made-up values, record them in a file of your own: `echo '{"rate_limits": {"five_hour": {"used_percentage": 95, "resets_at": <epoch seconds an hour from now>}, "seven_day": {"used_percentage": 10, "resets_at": <epoch seconds a day from now>}}}' | KEYTURN_USAGE_FILE=/tmp/usage.json python3 adapters/claude/scripts/usage.py statusline`, then run `check` and `hook` with the same `KEYTURN_USAGE_FILE` (an absolute path). To try the hook inside a session, set the variable before starting `claude`. To try a release, record values that have not reset yet, then run `release` with the same `KEYTURN_USAGE_FILE` in a terminal of your own: `check` then passes and the hook allows tool calls until the recorded reset time; record a new `resets_at` and both stop again. Inside a session started with that variable, ask the agent to run `usage.py release`: the hook must deny it. To try a plan without a 5-hour window, use a new `KEYTURN_USAGE_FILE` (a recording keeps a window the input leaves out) and record only `seven_day`: `check` stops, and passes with `KEYTURN_PLAN_WINDOWS=seven_day`. To try a usage check that cannot read the usage inside `deliver`, start the session with `KEYTURN_PLAN_WINDOWS=bogus` (a setup error that stops `check` while the hook still allows tool calls; a missing window does not work here, since the status line records it after the first response), and run the `deliver` trial: it must stop with `Stopped because: waiting for the maintainer` and the `stop:` line in `Can continue`, and `resume` must stop and ask the maintainer.

- Try the `go` profile in a scratch Git repository under `.keyturn/`, with Go and golangci-lint v2 installed: commit a `keyturn/config.json` with `"parts": [{"path": "api", "profile": "go"}]`, a `keyturn/internal/design.md` whose "QA's tests" table has `api/qa/**`, a `.golangci.yml` at the root, and a small module in `api/` with a test. Commit a change to the code and run `<keyturn>/gates/gate.sh --base <the commit before it>`: it must pass. Then each of these, in a commit of its own, must fail with exit code 1: a change that makes a test fail, an unused function (`lint`), a file `gofmt` would change (`format`), a deleted test function (`test-count`), a `//nolint` comment or a `// Code generated ... DO NOT EDIT.` line (`suppressions`), an `ignore` line in `go.mod` (`module`), and a change to `.golangci.yml` (`protected-paths`); the last passes when its commit is named with `--others conventions:<commit>`. A `go.work` at the root that names another module must not change the result. With `golangci-lint` not on `PATH`, the gate stops with exit code 2. To try the mark for QA's folders, commit, as `qa` (`--others qa:<commit>`), a test in `api/qa/` with an unused function and a test that reads `../../web/dist/index.html`: the gate must exit 1 with `FAIL lint [api] (QA's folders only)` and `FAIL test [api] (QA's folders only)`, and `"qa_only": true` on both in `--log`; then add an unused function to the developer's code in another commit: its `lint` line must not be marked, while `test` stays marked.
- Try the `react-spa` profile in a scratch Git repository under `.keyturn/`, with the newest LTS release of Node.js: commit a `keyturn/config.json` with `"parts": [{"path": "web", "profile": "react-spa"}]`, a `keyturn/internal/design.md` whose "QA's tests" table has `web/qa/**`, and in `web/` a small Vite React project in TypeScript 6 with the configs its README names (`eslint.config.js` whose `files` cover `**/*.{js,jsx,ts,tsx}`, `.prettierrc.json`, `tsconfig*.json`, `vitest.config.ts` that includes `src/**` and `qa/**` tests in `jsdom`, `.gitignore`), its `package.json` and `package-lock.json` with the profile tools installed at exact versions, a test in `src/`, and one in `qa/`. Commit a change to the code and run `<keyturn>/gates/gate.sh --base <the commit before it>`: it must pass and print a `VERSIONS [web]` line. Then each of these, in a commit of its own, must fail with exit code 1: a failing test, an ESLint error (`lint`), a file Prettier would change (`format`), a type error (`typecheck`), a deleted or `.skip`ped test (`test-count`), an `.only` test (`test`), an `eslint-disable` or `@ts-expect-error` comment (`suppressions`), a `.js` or `.mts` file the ESLint config does not cover (`lint`), a `vitest` dependency from a local folder or an alias, or an `npm-shrinkwrap.json` (`packages`), a file committed with `git add -f` under `dist/` or a `node_modules` folder (`files`), an `it.fails` test or a multi-line `/* eslint` comment (`suppressions`), an older version of a profile tool such as `prettier` installed by the developer (`pinned-tools`; the same change named with `--others conventions:<commit>` passes), an `eslint-suppressions.json` (`lint`, `protected-paths`), a new package whose `package-lock.json` entry has `"hasInstallScript": true` (`install-scripts`; it passes when an ADR accepted at the base, or at a commit named with `--others design:<commit>`, has `- Allows install scripts: <package>@<version>` for it, and fails when the line comes in a commit named with `--others conventions:<commit>`), a `package-lock.json` edited to drop `"hasInstallScript": true` from a package whose `package.json` has a `postinstall` script, such as `esbuild` (`install-scripts`), and a change to `eslint.config.js`, `vitest.config.ts`, `tsconfig.app.json`, or a new `.npmrc` (`protected-paths`). A `test.exclude` of `qa/**` in `vite.config.ts` must not stop a failing QA test from failing the gate. With `@playwright/test` installed as a profile tool, a QA Playwright test in `web/qa/e2e/` with a type error must fail `typecheck`, a failing one must not fail the gate (the gate runs no browser), and a change to the version of `playwright-core` must fail `pinned-tools`, and a `qa` commit that adds an image in another task's folder under `keyturn/client/evidence/` must stop the gate (exit 2). A `/* eslint-disable */` file in a folder that an ADR accepted at the base allows with `- Allows in web/src/gen/**: /* eslint-disable */` must pass. With `node` not on `PATH`, the gate stops with exit code 2.
- Try the gate in a scratch Git repository under `.keyturn/`: commit a `keyturn/config.json` with `parts` (for example `[{"path": "app", "profile": "<name>"}]`), a `keyturn/internal/design.md` with a "QA's tests" table, and a profile of your own in a folder of profiles (the tests in `gates/test_gate.py` have one that needs only Python). Then commit a change and run `<keyturn>/gates/gate.sh --base <the commit before it> --profiles <that folder>` there. A change that deletes a test, touches QA's folder, or adds a suppression comment without an accepted ADR on the same line must fail with exit code 1; a missing tool or a missing `parts` must stop it with exit code 2. A file that is not committed (for example, one listed in `.git/info/exclude`) must not change the result. A check that fails only because of a file in QA's folders, committed as `qa`, must be marked `(QA's folders only)` on its `FAIL` line, with exit code 1; the same failure in a developer's file, or in both, must not be marked, and neither may `protected-paths` nor `test-count`. To try `--others`, commit a change under QA's folder and pass that commit as `--others qa:<commit>`: the gate must pass, and must stop with exit code 2 if the same commit also changes a file outside QA's folders. In the same way, a commit that changes only `keyturn/internal/design-answers.md`, named as `--others answer:<commit>`, even after a developer commit, must pass, and one that also changes `keyturn/internal/design.md` must stop it with exit code 2, while a developer commit that changes the answers fails `protected-paths`. To try the way CI calls it, run `<keyturn>/gates/gate.sh --task <task> --default-branch main` on a task branch that `deliver` ran to at least `implement` (for example, the one from the `deliver` trial): it must give the same result as `deliver`'s own call. Then commit a change to the state file that relabels an `implement` commit as `qa`'s, or names a later commit as `conventions`', and run it again: it must stop with exit code 2. To try a redo before `implement`, on another such branch before `implement`, set `design` and `conventions` back to `not started` in a state commit, commit a design change and a state commit listing it as `design`, then a conventions change and a state commit listing it as `conventions` with `conventions` done, then a developer commit: `--task` must stop with exit code 2, and pass with `--documents-vouched <task>:<the full SHA of the last state commit before the developer's>`; that same option naming a state commit after the developer's must stop it.
